# sflow 规格驱动 AI 工作流 - @eddadd/sflow

> 一套规格驱动的 AI 编程工作流——**让 AI 在被批准的契约内写代码**，用确定性的机械护栏替代概率性的 prompt 约束。

sflow 把"先想清楚、再写代码"钉成一条流水线：规划（proposal / specs / tasks，design 按需）→ 执行契约硬门禁 → 按批次实现 → 真实验证 → 审查 → 归档合并主规格。本 CLI 把 8 条 `/sflow-*` 命令一键分发到你的 AI 客户端技能目录。

---

## 为什么需要 sflow

AI 辅助编程的失控，归根结底是两类：**方向失控**（需求没想清楚就动手）和**执行失控**（规划写得再好，执行照样跳测试、擅自改 API、顺手改范围）。展开来看是六个反复出现的痛点：

1. **需求理解偏差**——AI 拿到一句话需求就开始写，方向错了才发现
2. **范围蔓延**——"顺手改一下"，改 A 带坏 B，改动面不受控
3. **虚假完成**——声称"已完成、测试通过"，实际从未真实运行验证
4. **契约漂移**——做到一半需求和方案悄悄变了，没人意识到计划过期
5. **状态丢失**——会话中断后 AI 不知道做到哪一步，重复劳动或跳步
6. **规格腐烂**——文档写完一次就扔，代码迭代几轮后与实现完全脱节

靠提示词"叮嘱" AI 遵守规则是不可靠的——自然语言约束会随上下文漂移。sflow 的核心思路：**把约束从"聊天里说"变成"流程里钉死"**。

## 设计初衷

**骨架来源**：两个被实践验证过的关键设计——

- **桥接契约层** → `execution-contract.md`：把规划工件压缩成可执行契约，作为规划到实现的唯一交接层，**契约未批准，一行业务代码都不许写**；
- **状态路由引擎** → 8+2 状态机：**大阶段**从工件内容推断，**阶段内位置**从 `state.yaml` 回执末条确定（无 `state.yaml` 的存量变更回退 progress.md 台账末行），都不从聊天记忆推断——**会话断了也能续上**。

**前身沉淀**：sflow 脱胎于两个实战 skill，继承其精华、重构其局限——

- **openspec-spec-methodology**（规划侧前身）：三支柱增强预检（复杂需求拆解 / 契约与承载预检 / 颗粒度与边界校准）被完整继承，内置进 `sflow-propose` 成为强制环节；
- **glodrapay-front-test**（验证侧前身）："依验收标准逐条核对 + 真实执行测试"的核心打法被保留，从单项目固定技能重构为可插拔挂载的通用测试能力。

**四条核心初衷**：

1. **把概率性约束变成确定性纪律**——工件指纹（`artifacts` / `tasks` / `contract` 三段指纹，漂移即机械判定契约过期）、机械校验 CLI（`sflow state` / `validate` / `guard` 把状态推断、回执校验、指纹与锚点判定交给程序，不靠人眼）、check-only 验证链（只读不写，防 `--fix` 污染判定）；
2. **人工决策点分级**——4 个 DP 中只有 DP-2（契约批准）是唯一硬门禁、永不轻量化；其余按场景减负，快速路径只豁免文书、**永不豁免验证**；
3. **项目专属能力与通用工作流分离**——本体平台无关，项目差异收敛到 `workflow.config.md`，增强不被静默跳过；
4. **从个人流程到可分发产品**——`npx` 六端一键安装，配置模板自带概念速览，不读源码也能上手。

**三条设计底线**（不受任何路径与开关影响）：

1. 未经批准的契约，不写一行业务代码
2. 任何"通过"必须附真实执行输出
3. 快速路径超出边界，自动升级回完整流程

## 它是怎么工作的

```
规划 → 契约 → 执行 → 验证 → 审查 → 归档
（8 条命令：start / propose / contract / apply / debug / verify / review / archive）
```

- **仅 4 个人工决策点（DP-1~4）**：需求确认、契约批准、调试升级、归档确认。人只管关键拍板，其余全部自动化。其中两个按场景条件化——**DP-1** 对一句话能说清的简单 full 需求可跳过（跳过写 `dp1.skipped` 回执），**DP-4** 对纯新增且标题无冲突的 delta 可直通合并；**DP-2 永不轻量化**；
- **范围栅栏**：只允许修改契约中列出的文件，范围外改动强制回退重新规划，禁止"顺手改"；
- **提交纪律（可选）**：`git_discipline: on` 时每批次走 TDD 红-绿（先失败测试 → 最小实现 → 转绿 → commit）并要求工作区干净；默认 `off`，不改变你的提交习惯——**开关不豁免验证**；
- **真实验证纪律**：验证链逐条真实执行并贴出输出，配合深度验证（可挂载 glodrapay-front-test 等测试技能）与三维判定（完整性/正确性/一致性），一致性以 `git diff --name-only <review_base>` 的真实改动比对契约，不用 AI 自述清单；
- **审查是必经门禁**：验证通过后路由到 `/sflow-review`（不是直接归档），审查结论无阻塞 Critical 才允许归档；
- **状态回执（state.yaml）**：与 progress.md 同级、append-only——**锚点**（`review_base` + 三组工件指纹，只写一次）与**回执**（`dp1.approved` / `dp1.skipped` / `dp2.approved` / `batch.N.done` / `verify.passed` / `review.passed` / `debug.attempt.N` / `archive.direct` / `archive.done` / `path.selected`）分列，状态判定与"改没改过基线"都由它机械读出，归档时随目录整体移动；
- **机械校验 CLI**：`sflow state`（推导阶段与下一步）、`sflow validate`（校验回执自洽：伪回执 / 锚点 / 结构头）、`sflow guard`（契约新鲜度 + 锚点完整性）、`sflow guard --emit-fingerprints`（DP-2 生成回执行，替代手抄哈希）——只读、退出码即结论（`guard` 1=过期 2=污染），AI 不再"读散文猜状态"；
- **全程台账（progress.md）**：批准叙述、批次改动清单、验证输出、调试尝试全部留痕，**可恢复、可审计**（与 state.yaml 分工：state.yaml 存"发生了什么"，progress.md 存"怎么发生的"）；
- **调试升级（DP-3）**：连续失败次数由 `counters.debug_attempts` 机械计数（不再靠人眼数段落），达到阈值强制停下交人决策，禁止无限盲试；
- **防规格腐烂**：归档时 delta 规格合并回主规格，历史变更封卷留档。

## 安装

```bash
# 无需全局安装，直接使用
npx @eddadd/sflow init

# 或全局安装
npm install -g @eddadd/sflow
sflow init
```

## 支持的目标

路径规则为 `~/.<target>/skills/`（例外见下），指定目标用 `--target`：

| 目标             | 目录                   | 命令                            |
| ---------------- | ---------------------- | ------------------------------- |
| agents           | `~/.agents/skills/`    | `sflow init --target agents`    |
| claude           | `~/.claude/skills/`    | `sflow init --target claude`    |
| codex            | `~/.codex/skills/`     | `sflow init --target codex`     |
| workbuddy        | `~/.workbuddy/skills/` | `sflow init --target workbuddy` |
| trae（例外）     | `~/.trae-cn/skills/`   | `sflow init --target trae`      |
| opencode（例外） | `~/.config/skills/`    | `sflow init --target opencode`  |
| 任意目录         | 自定义路径             | `sflow init --dir <path>`       |

**不带 `--target` / `--dir` 时不会猜错地方**：`init` 会先探测本机哪些客户端目录已经装过 `sflow-*`，把它们**全部同步一遍**；一处都没装过才回落到默认目标 `agents` 做首次安装。想一次性铺满全部 6 个目录用 `--all`。

每次安装会在目标目录写 `.sflow-install.json` 清单（版本 / 时间 / 技能列表），下次 `init` 据此播报真实版本变化，例如：

```text
目标：workbuddy  C:\Users\song\.workbuddy\skills
  ✔ sflow-apply
  ...
  版本：v0.1.3 → v0.2.1（8 条技能）
```

复制前会清理目标目录里源模板已不存在的孤儿文件，避免跨版本升级时新旧文件混杂（`sflow-start/assets/` 等生成物除外，它们由安装时重新生成）。

## 使用方式（三步上手）

**第 1 步：安装技能（一次性，无需进项目）**

```bash
npx @eddadd/sflow init                  # 探测已装目录并全部同步（首次装到 ~/.agents/skills/）
npx @eddadd/sflow init --target claude  # 只同步指定客户端
npx @eddadd/sflow init --all            # 强制写入全部 6 个目标目录
npx @eddadd/sflow init --config         # 顺带在当前项目生成 workflow.config.md 配置模板
```

**第 2 步：配置项目（每个项目一次）**

编辑项目根目录的 `workflow.config.md`，声明四件事：**验证链**（lint / typecheck / test 等命令）、**测试与审查工具**（如 glodrapay-front-test、code-cr，可留空走内置默认）、**快速路径边界**（tweak / hotfix 的文件数阈值）、**提交纪律开关**（`git_discipline`，默认 `off`；设为 `on` 后每批次走 TDD 红-绿并要求工作区干净 + 每批 commit）。

**第 3 步：日常使用（在 AI 客户端里对话即可）**

| 场景     | 你做什么                                                        | 背后发生什么                                                          |
| -------- | --------------------------------------------------------------- | --------------------------------------------------------------------- |
| 提新需求 | 说一句 `/sflow start`                                           | 自动检测状态、按工作量推荐路径（tweak / hotfix / full）并路由到下一步 |
| 正式需求 | 依次执行 propose → contract → apply → verify → review → archive | 每个阶段在人工决策点停下等你拍板，契约批准前不写一行代码              |
| 小改动   | 直接说需求，走快速路径                                          | 只留台账 + 真实验证，不写规划工件，不被流程拖累                       |
| 会话中断 | 重开后再说 `/sflow start`                                       | 从工件与 `state.yaml` 回执恢复进度，接着上次继续，不重做不跳步        |

全程不需要记命令顺序——每条命令结束都会输出阶段报告，明确告诉你下一步该执行哪条。

## 命令

| 命令           | 说明                                                                     |
| -------------- | ------------------------------------------------------------------------ |
| `sflow init`   | 安装/覆盖 8 条技能：探测已装目录全部同步，无则装到 `agents`；`--config` 额外生成 `workflow.config.md` 模板 |
| `sflow update` | 同 `init`，语义化别名                                                    |
| `sflow list`   | 查看各目标的版本、完整度与是否最新                                       |
| `sflow remove` | 卸载已安装的 `sflow-*` 技能（目标解析同 `init`）                         |

## 安装后你会得到什么

8 条技能命令，覆盖工作流全生命周期：

```
/sflow-start     入口与状态检测（含恢复中断会话）
/sflow-propose   规划阶段：澄清需求 → proposal/specs/tasks（design 按需）（DP-1 确认，简单需求可跳过）
/sflow-contract  桥接阶段：生成执行契约（DP-2 批准，唯一硬门禁）
/sflow-apply     执行阶段：按契约批次实现，范围栅栏 + 工件指纹核对 + 锚点完整性核对（可选 TDD/commit 纪律）
/sflow-debug     调试阶段：四阶段根因分析，3 次失败升级 DP-3
/sflow-verify    验证阶段：真实验证链 + 三维判定
/sflow-review    审查阶段：可插拔接 code-cr 等审查工具
/sflow-archive   归档阶段：delta 合并回主规格（DP-4 确认，纯新增可直通）
```

CLI 侧另有 4 条机械校验命令：`sflow state` / `validate` / `guard` / `guard --emit-fingerprints`（见上「机械校验 CLI」）。

加上共享约定 `core.md`（状态机 / 决策点 / 强制回退 / 阶段报告 / 状态回执 / 结构头规则 / 机械校验 CLI）与项目配置模板 `workflow.config.md`。

每个变更目录里除规划工件与契约外，还有两份台账：`state.yaml`（机器可读的状态回执）与 `progress.md`（人可读的过程证据）。

## 核心优势

1. **确定性 > 概率性**：关键判定（指纹比对、状态推断、门禁拦截）全部交给机械校验 CLI，AI 只能执行，不能"自我解释地绕过规则"；
2. **人的注意力花在刀刃上**：人只在 4 个决策点介入，每次都有结构化摘要辅助决策；
3. **质量前移**：问题在规划/契约阶段就被拦住，比写完再改的成本低一个量级；
4. **可审计**：每个变更从提出到归档全程留痕，归档目录是天然的审计证据与复盘材料；
5. **跨平台可复制**：一套方法论打包成 CLI，一条命令即可获得相同的工作流；
6. **务实不教条**：快速路径、轻量化开关、可插拔工具，平衡"控制力"与"灵活性"。

## 路线图

- **短期（度量闭环）**：从 progress.md 台账提炼效能指标（返工次数、DP 拒绝率、调试失败率、交付周期）；
- **中期（团队化）**：多角色并行规划、主规格冲突治理、与 Git 分支模型对齐；
- **长期（平台化）**：契约门禁接入 CI/PR（契约指纹校验、范围比对自动化），形成"AI 写码、流程把关、人做决策"的研发工作流范式。

## 开始使用

安装后，在你的 AI 客户端中说：

```
/sflow start
```
