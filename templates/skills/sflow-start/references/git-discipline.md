# 提交纪律（/sflow-apply 专用，按需加载）

本文件是 core.md 第 12 节的正文本体。只有 `/sflow-apply` 需要加载它——其余命令不必读，以保持每次会话的上下文开销最小。

## 开关

由 `workflow.config.md` 的 `git_discipline` 控制，默认 `off`。

**为什么默认 off**：TDD 红-绿与每批次 commit 会改变使用者的 git 习惯与提交粒度。强制开启会让「流程保护」变成「流程摩擦」，尤其在存量项目、脏工作区或已有既定提交规范时。因此设计成**显式开启**的能力，而不是默认强加的纪律。

**开关不改变底线**：无论 `off` 还是 `on`，以下三项永远强制——

1. 验证义务必须真实执行并贴输出（core.md 第 7 节）；
2. 每批次完成必须写 `batch.N.done` 回执（core.md 第 11 节）；
3. 契约指纹与锚点核对（core.md 第 3 节）在每批次开始前照做。

`git_discipline: off` 只是**不强制**「先写测试」与「每批 commit」，不是允许跳过验证或回执。

## `git_discipline: on` 时的三条硬约束

| 约束 | 时点 | 命令 / 判据 |
|------|------|------------|
| 干净树前置 | 每批次开始前 | `git status --porcelain` 无输出；有未提交改动 → 拒绝进入批次，先让用户处理（提交或暂存），不得「带着上次的残留继续」 |
| TDD 红-绿 | 每批次内 | 先写会**失败**的测试并贴出失败输出（红）→ 最小实现 → 测试转绿并贴出通过输出（绿）。测试无法先行时（纯配置/文档/无测试框架）如实记录豁免理由，不得假装红过 |
| 每批次 commit | 每批次收尾 | 验证义务通过后 `git commit`，提交信息含批次号与覆盖的 Requirement；提交后再写 `batch.N.done` 回执（回执记录 commit sha 作为证据） |

## 与 review_base 的顺序

批次 commit 会推进 HEAD，但 `baseline.review_base` 是 DP-2 批准时的起点 sha，**不随之改变**（core.md 第 3 节）。验证与审查始终以 `review_base..HEAD` 为真实改动范围——每批 commit 恰好让这段 diff 更清晰，而不是让基线漂移。

## TDD 红-绿的证据形态

贴进 progress.md，回执只记摘要：先贴失败用例名 + 失败输出片段，后贴同一用例通过输出。**禁止**只写「已按 TDD 完成」而无失败阶段的输出——那是自述，不是证据。
