# sflow-debug

调试阶段：先找根因，再动手修。连续修不好不是继续盲试的理由，是升级给用户的信号。

## 进入方式

从 `/sflow-apply`（执行中遇 bug）或 `/sflow-verify`（验证失败）转入。进入时先在 progress.md 记录：症状、失败命令与输出、触发批次。修复完成后返回来源命令继续。

## 四阶段根因分析

1. **根因定位**：读报错/复现路径，定位到具体代码与数据流；禁止把"表象"当根因（如"样式不对"不是根因，"类名被 stylelint 重排序导致覆盖失效"才是）。
2. **模式分析**：这是首犯还是同类问题复发？是否与既往变更/约束冲突？涉及公共组件或全局样式时评估影响面。
3. **假设**：写出一句话根因假设，并说明"改哪里、为什么这样改能消掉症状"。
4. **最小修复**：按假设实施最小改动；同步评估是否引入新魔法值/破坏项目规范。

修复后必须跑对应验证（批次验证义务或验证链相关项），真实输出贴进台账。

## 修复尝试台账（progress.md 追加）

每次尝试记录一条，缺一不可：

```
### Attempt <n>：<一句话假设>
- 改动：<文件 + 要点>
- 结果：<通过/失败，附关键输出>
- 证据：<退出码、报错摘要或验证输出>
```

**硬规则**：没有台账记录不得进行下一次尝试；结论相同的重复尝试直接拒收；臆测"应该能行"不构成假设——假设必须能被证伪。

## DP-3：调试升级（3 次失败强制触发）

连续 3 次有台账记录的修复尝试失败：

1. 停止一切修复动作。
2. 向用户呈报：三次尝试的假设/改动/结果汇总、根因分析的当前结论、剩余可行方向（如有）。
3. 由用户决策：继续当前方向 / 换方向重试 / 质疑架构回 `/sflow-propose` 或 `/sflow-contract` / 放弃变更（abandoned）。

**硬规则**：DP-3 未经用户表态，不得开始第 4 次尝试。

## 阶段报告（强制收尾）

输出末尾必须附共享约定 core.md（sflow-start 母本）第 8 节的四行报告。"下一步"按结果写：修复通过 → 返回来源命令；3 次失败 → 等待 DP-3 用户决策。

## 反模式

- 不得跳过根因直接改症状（加个 try/catch 掩盖、改个样式硬盖）。
- 不得连续重试同一思路——每次尝试必须基于新假设。
- 不得把"升级"当失败——3 次修不好通常说明假设层错了，升级正是流程在保护你。
