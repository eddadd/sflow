# spec 增强方法论（sflow-propose 内置）

本文件是 `/sflow-propose` 的内置增强方法论，提炼自 openspec-spec-methodology（v1.7）并适配 sflow 工件体系。目标：**在写任何工件之前，把需求质量提升到「AI 依 spec 实现不跑偏」的可验证水平**。工件仍由本命令按 sflow 模板产出，本文件只提供写之前的增强预检纪律。

适用对象：中等以上复杂度需求（多模块动点、含隐性约束、有跨模块契约、状态时序敏感）。简单需求（单文件、无交叉约束）按"粒度判断"可豁免，见下文。

---

## 一、复杂需求拆解（支柱一）

### 1.1 四层拆解

把原始需求强制拆为四层，任何一层缺失都视为拆解不完整：

| 层级 | 含义 | 拆解产物 |
| ---- | ---- | -------- |
| 能力层 | 本次变更提供什么能力边界（做什么 / 不做什么） | 能力列表 + 明确的「不做」清单（落入 proposal Out of Scope） |
| 需求层 | 每个能力分解为可独立验收的需求条目 | Requirement（落入 specs delta） |
| 场景层 | 每条需求分解为行为化的场景 | `#### Scenario:` 矩阵 |
| 边界层 | 每个场景下的边界分支 | 独立场景条目（见支柱三） |

### 1.2 强制识别三种隐性需求

拆解时不能只做「正向翻译」，必须主动挖出三种容易遗漏的隐性需求：

1. **逆向约束（禁止什么）**：需求说「新增详情页」→ 隐含「侧边栏禁止出现入口」。这类必须显式写成 `禁止` / `必须不` 形式的场景。
2. **跨模块契约**：路由、query 参数、接口数据流、动态路由权限过滤、keepAlive 缓存、共享枚举常量。这类牵一发动全身，必须在影响分析里点名到具体文件。
3. **交互时序**：先做什么后做什么（如「先选业务线 → 再拉支付方式类型选项 → 业务线变更清空已选」），时序错乱是 AI 跑偏的高发区。

### 1.3 决策点显式化

拆解中遇到的「二选一 / 多选一」决策必须：在 proposal/design 中**显式声明选择**并给一句理由；一经选定，spec 中所有相关场景统一约束，禁止前后矛盾。

### 1.4 字段关联性显式化

新增多个表单字段或接口参数时，必须显式声明字段间的关联/独立关系：

- **关联字段**：A 变化时 B 必须跟着变。逐一列出「A→B」联动对，写进 spec 场景与 design 决策。
- **独立字段**：A 变化时 B 不受影响。逐一列出「A 不影响 B」独立对，写进 design 决策，避免实现时误清空。

### 1.5 取值形态与承载组件能力双核对

新增字段由既有组件承载（下拉框、表格、日期选择器等）时，预检阶段必须核对**两件事**，任一遗漏都会在实现时踩坑：

#### 1.5.1 取值形态 vs 组件入参类型

- 字段是布尔值、数值枚举、字符串枚举还是对象？下拉选项的 `value` 用哪种形态？
- 承载组件的绑定 prop 类型是否接受该形态（如共享组件 `FsSelect` 的 `selectValue` 为 `String | Number | Array`，不含 `Boolean`，布尔 value 会触发 Invalid-prop 告警）。
- 不兼容时在预检阶段就声明二选一——①扩展共享组件类型（注意 Vue 的 Boolean casting 副作用）；②改变取值/提交形态（如「下拉传 `1/0`，提交时转布尔」）——选定后写进 design 决策，全篇统一。

#### 1.5.2 所需能力 vs 组件是否支持

计划让某个共享组件承担一项功能时，必须先确认该组件**是否透传 / 是否提供**这项能力，不能假定「同族组件都一样」：

- **插槽透传**：如 `fs-table` 只透传 `bodyCell` / `headerCell` 两个具名插槽，**不透传 `expandedRowRender`**；需要展开行时必须直接用 `a-table`。
- **能力开关**：分页、展开行、虚拟滚动、可编辑单元格等，使用前逐一核对目标组件 props / slots。
- **预检动作**：写下「用 X 组件实现 Y 能力」前，先定位该组件的 props/slots/透传清单（读组件源码或 `.d.ts`），确认能力存在再落笔；不支持则显式声明替代方案。

### 1.6 同名字段多来源一致性核对

同一业务字段在**多个接口**返回时（如列表与详情接口各自返回），预检阶段必须显式声明：来源清单、一致性口径（以哪个接口为准；前端无法仲裁则挂一条跨接口一致性核对任务）、多消费点判定口径归一化（如统一 `=== true`）。

### 1.7 接口返回结构预检

除字段名外，每个接口的**返回结构形态**与**字段归属**也必须在预检阶段显式声明：

- **返回结构形态**：列出每个接口返回的是「分页对象（`records`+`total`）」「单对象」「数组」还是「无返回」；数组接口要写明「元素结构」。
- **字段全集归属**：列表接口与详情接口字段高度重叠时，必须显式声明「哪组字段由哪个接口返回」——是「列表项仅摘要、详情返回全集」，还是「列表项已内嵌完整详情字段、详情接口另返回数组」？**禁止凭「列表该瘦、详情该全」的直觉反推契约。**
- **同名不同义**：同一名称的枚举在不同字段下语义可能不同（如 `PENDING` 在订阅状态=「处理中」、在扣款状态=「下单中」；「失败」取值订阅用 `FAILED`、扣款用 `FAIL`）。发现同名或近名枚举，逐一核对归属与取值，不做合并。

### 1.8 粘贴契约的字段归属核对

用户常直接**粘贴接口文档 / 枚举定义片段**作为需求输入。粘贴内容可能与字段实际归属不符（笔误、复制残留、命名重复），预检时必须核对而非照抄：

- **同名标注核对**：同一份粘贴内容里多组枚举被标注为同一字段名时，必须按**语义**判断归属并向用户确认，禁止照抄标注。
- **语义与字段名不符**：某组取值语义明显不属于其标注字段时，主动指出并提问。
- **不猜**：字段归属属于业务契约，粘贴标注有冲突时先问再写进类型定义，防止错误契约污染 spec / 设计 / 类型。

### 1.9 未点名控件默认文本输入框

筛选 / 表单字段若未在需求里显式声明控件类型（下拉 / 日期 / 开关），**默认按文本输入框实现**，并在预检结论里显式列出「哪些字段是下拉（及选项来源）、哪些是日期、其余为文本」作为可核对清单。实现者容易把「枚举类字段」惯性做成下拉，但用户可能只要一个文本搜索框。

### 1.10 新建页面/详情页的要素默认值确认

新建列表页、详情页时，以下要素属于**用户可控项**，预检阶段应逐项确认默认值，把易返工项前置到同一轮对话：

- **详情页**：是否用 `<a-card>` 承载、右上角是否放「返回」按钮（返回目标）、导出按钮位置（`extra` 插槽）与入参范围、列表是否分页、展开行数据结构。
- **列表页**：时间列位置（首列/末列）、操作列按钮、字段顺序。
- **导出**：入参是「仅主键」还是「带当前筛选条件」。

## 二、颗粒度标准（支柱二）：AI 不跑偏的可验证阈值

### 2.1 组成式场景（当/那么/并且）

每条需求必须拆成独立场景，写在 `#### Scenario:` 块内：

- **当（Given）**：前置状态/输入条件，必须可构造。
- **那么（Then）**：系统行为，必须可观察（渲染、跳转、请求、隐藏），禁止「正常处理」「合理展示」这类自评词。
- **并且（And）**：并列行为结果，一条场景可叠加多条。

### 2.2 可量化验收点

每个验收点必须给出**可核对的量化标准**，而不是「能正常显示」：

- 可数：字段数量、区块数量、请求次数、枚举项数量（如「概览区展示 5 个字段」「请求调用次数为 1」）。
- 可对照：同数据源新旧实现逐项比对。
- 可检索：全仓检索某符号无残留引用、某枚举未重复定义。
- 可观测：打开某页签时才发起某请求、切走再切回不重复请求。

### 2.3 自我验收措辞禁令

以下措辞在 spec 中**禁止出现**，出现即视为颗粒度不足，必须改写成可验证描述：

`合理即可` · `正常展示` · `妥善处理` · `美观` · `友好提示` · `不报错`（需改为「不抛错且展示空内容」这类行为描述）· `视情况` · `尽量`

## 三、边界条件铺排（支柱三）

### 3.1 强制边界场景清单

每个需求模块写 spec 时，以下边界必须**逐一过一遍**，凡适用即写成**独立 `#### Scenario:`**（禁止塞进正常路径当一句注释）：

| 类别 | 边界 | 场景措辞示例 |
| ---- | ---- | ------------ |
| 空值 | 字段 / 区块 / 数组缺省 | 值为 `null` / `undefined` / `''` 时展示 `--`；区块数据缺失时不渲染标题且不报错 |
| 非法值 | 枚举不在映射表 | 非法枚举值不导致报错，展示兜底文案 |
| 失败态 | 请求失败 / 接口报错 | 请求失败展示空数据提示，页面其余部分可交互 |
| 空选项 | 下拉接口返回空数组 | 下拉为空且页面不报错 |
| 时序 | 首次进入 / 切走切回 / 往返切换 | 未访问不请求、首次访问才挂载、已加载不重复请求 |
| 权限 | 动态路由过滤 / 无权限 / 隐藏路由未授权 | 后端未返回菜单项时路由不注册、直接访问走 404；新增 `hideInMenu` 详情路由时，预检阶段必须抛「后端菜单是否返回该路由 name」让用户选定放行方式（后端补权限 / 挂子路由复用父权限 / 加入临时白名单） |
| 串号 | 切换主体 / keepAlive 缓存 | 切换商户时数据不串号；未开缓存时切回重新请求 |

### 3.2 边界表达三原则

1. **独立场景化**：每个边界是独立场景，与正常路径并列。
2. **可触发前置**：边界场景的「当」必须描述如何构造该边界。
3. **结果可观察**：边界的「那么」必须说明系统在该边界下如何表现。

### 3.3 验收标准的边界挂载

每个区块/模块的验收标准**必须包含边界条目**（格式 `边界：<行为描述>`）；涉及接口调用次数的，把「N 次」写进验收标准；所有边界验收标准也必须可量化。

## 四、验收标准面向测试消费

本命令产出的 tasks.md 验收标准，在验证阶段会被测试工具（config「测试工具」，或内置默认深度验证）消费并生成测试。因此验收标准必须：

- **可转断言**：每个验收点是可判定的布尔条件（`请求恰 1 次`、`按钮不渲染`、`入参不含 page`），而不是方向性描述（`应当能导出`）。
- **独立成条目**：验收点逐条列出，不揉进叙述段落，便于逐条转成用例。
- **不依赖实现细节**：描述「外部可观察行为」（渲染/请求/文案/权限显隐、请求次数、入参内容），禁止把内部实现（具体函数名、switch 写法）作为验收条件。
- **与 spec 场景互补**：spec 场景（`#### Scenario:`）约束行为，验收标准约束「如何验证」，两者同时存在，缺一不可。

## 五、OpenSpec 兼容预检（写工件前扫描主 spec）

涉及既有主 spec 的变更，写工件前对其做一次格式兼容性扫描，避免归档合并失败：

1. **章节头格式**：主 spec（`openspec/specs/<capability>/spec.md`）的需求章节头必须是 `## 需求`；`## 新增需求`、`## 需求列表` 等变体不被解析器识别，发现即在预检结论中标注修正。
2. **delta 标题格式**：MODIFIED/ADDED 的需求标题必须与主 spec 既有标题逐字一致（`### 需求:<名称>` 中文冒号格式），禁止 `### Requirement:` 英文格式——归档按标题精确匹配，英文标题会导致找不到目标需求。

## 六、增强预检清单（写工件前逐条过验，任何「否」先修正）

- [ ] A1 需求已拆为「能力 / 需求 / 场景 / 边界」四层，无缺失层
- [ ] A2 已列出明确的「不做」清单（落入 Out of Scope）
- [ ] A3 已识别逆向约束并拟成独立场景
- [ ] A4 已点名跨模块契约涉及的具体文件
- [ ] A5 已显式声明每个决策点（选 A 不选 B + 一句理由）
- [ ] A6 已显式声明字段关联性（联动对 + 独立对）
- [ ] A7 已核对新字段取值形态与承载组件的入参类型约束，不兼容已声明采用「扩展组件」还是「改传值形态」
- [ ] A8 同名字段多来源已列来源清单 + 一致性口径 + 判定口径归一化
- [ ] A9 已核对承载组件是否提供计划用到的能力（插槽透传、展开行、分页开关等），不透传已声明替代方案
- [ ] A10 已核对每个接口的返回结构形态（分页对象/单对象/数组）+ 字段全集归属，列表/详情字段重叠时已显式声明归属
- [ ] A11 用户粘贴契约/枚举片段时，已核对字段归属（同名标注冲突、语义与字段名不符），不照抄标注、不确定先问

- [ ] A13 新建页面/详情页要素默认值已逐项确认（返回按钮/卡片结构/导出位置与入参/列表分页/展开行结构/时间列位置）

### B. 颗粒度可验证

- [ ] B1 每条需求已拆成可独立验收的场景，无糊块
- [ ] B2 场景「当」可构造、「那么」可观察
- [ ] B3 验收点可量化（有可数指标）
- [ ] B4 涉及新旧并存时，有「逐项对照」类比对标准
- [ ] B5 全文无自我验收措辞
- [ ] B6 工件正文使用中文书写（强制技术标识符除外）

### C. 边界覆盖

- [ ] C1-C7 七类强制边界（空值/非法值/失败态/空选项/时序/权限/串号）凡适用已写独立场景；C6 权限含 `hideInMenu` 隐藏详情路由的后端菜单 name 预检确认
- [ ] C8 每个模块验收标准包含 `边界：` 条目，且可量化

### D. 配合与产出

- [ ] D1 预检结论已落入工件对应位置（proposal 的决策、design 的约束、specs 的场景、tasks 的验收标准）
- [ ] D2 验收标准独立成条目、可转断言、不依赖实现细节，可供测试工具消费
- [ ] D3 验收标准与 spec 场景互补，两者同时存在
- [ ] D4 OpenSpec 兼容预检已执行（主 spec 章节头 + delta 标题格式）

## 粒度判断（豁免规则）

单文件、无交叉约束的小改动可跳过增强预检直接写工件，但在 DP-1 展示时注明「简单需求，未执行增强预检」。判不准 → 按执行预检处理，宁可预检空转，不要边界裸奔。
