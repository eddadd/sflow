# sflow-verify

验证阶段："完成"不是声称出来的，是跑出来的。本命令是收口前的最后一道硬门禁。

## 前置检查

1. 加载共享约定 core.md（单一母本：`sflow-start/references/core.md`，本目录不再保留副本）与项目 `workflow.config.md`。
2. 状态检测：tasks.md 全部勾选，且 state.yaml 回执流末条为 `batch.N.done` 或 `debug.resolved`（验证→调试→重验的循环修复完成）（无 state.yaml 的存量变更以 progress.md"执行完成"为准）；若末条已是 `verify.passed`/`verify.failed`，说明验证已发生过 → 默认不重复验证，如实告知用户并请其确认是否重跑。未执行完成 → 拒绝验证，输出阶段报告指回 `/sflow-apply`。

## 验证链执行（核心动作）

1. 默认选择**标准模式**，仅当用户明确要求“全量测试”或“完整验收”时选择**完整模式**；工作流 full/tweak/hotfix 是路径而非测试模式，不影响选择。仅要求“生成测试报告”且未指定模式时先询问标准或完整，并说明完整模式执行全量测试、lint、typecheck、build。
2. 从 `workflow.config.md` 的“标准验证链”或“完整验证链”读取对应检查。标准链先确定范围：用户指定范围优先；否则结合 `baseline.review_base` 到 HEAD、暂存、未暂存和未跟踪文件，按当前变更契约、验收标准及关联测试确认；缺基线或关联不可靠时询问用户。不得把空范围传给测试框架或悄悄改跑全量。标准链只执行已确认的范围检查；不得默认执行全量测试、全项目 lint/typecheck 或 build。若必需检查只能全项目执行，向用户说明并请求单项确认；未执行则记录未完成，不得声称该链通过，也不得将单项确认称为完整验收。
3. 旧配置只有“验证链”时，将其视为**完整链**，不得原样当标准链执行；标准模式根据项目框架确定可执行的定向检查并经用户确认，无法确定则停止并说明迁移需求。完整模式仍按旧链执行。配置缺失或所选链无法确定时停止，不得猜测通过。
4. **每条适用的所选链检查真实执行**，完整贴出命令、实际范围与输出（包括无输出时的退出码）；明确记录不适用、未执行及原因。测试失败或零用例不算通过。
5. 任何一条失败：
   - 在 state.yaml 追加 `verify.failed` 回执（含失败命令）
   - 在 progress.md 验证记录表登记失败详情
   - 触发 DP：向用户呈报失败项，由用户决定转 `/sflow-debug` 修复后重验，还是放弃变更
   - **不得**自行重试超过一次，不得跳过失败项继续判"通过"
6. 所选链、深度验证及适用三维判定全部通过后，才在 state.yaml 追加 `verify.passed` 回执；在 progress.md 逐条登记时间、模式、基线、范围、命令、结果及未执行项，注明“标准范围验证通过”或“完整验证通过”，不得把前者称为全量通过。

## 深度验证（可插拔 + 内置默认）

验证链全部通过后，读取 workflow.config.md「测试工具」配置：

**配置了测试技能（如 glodrapay-front-test）**：

1. 加载该技能，传入已选模式、范围及本轮验证证据；定位本变更验收依据，按该技能走查、测试并生成报告。若本轮同范围测试已真实执行且相关源码、测试和配置均未改变，可复用其结果；新增或修改测试后定向重跑受影响测试，完整模式下必要时重跑全量。不得复用过期证据。
2. 测试报告路径与结论记入 progress.md 验证记录表；断言明细与走查证据作为下方三维判定 Correctness 的依据。
3. 走查发现的 R 级问题按该技能清单登记：R1（功能错误）视同验证失败，触发 DP；R2/R3 呈报用户——确认修复则回 `/sflow-apply` 或 `/sflow-debug` 后重验，确认延后则记录后放行。
4. 技能不可用（未安装/加载失败）→ 明确告知用户，不得静默跳过；用户确认后可转内置默认验证和报告，并记录替代方式，不得凭未执行的验证宣布通过。

**未配置（留空）→ 内置默认深度验证**（不得直接跳过）：

1. 以 tasks.md 验收标准编号为依据，逐条生成核对结论：
   - 可用项目测试框架（验证链中的测试命令）验证的 → 依验收标准编写测试用例并真实执行，贴出输出；
   - 只能走查核对的（UI 呈现、文案、样式）→ 逐条走查实现代码，贴出代码位置与判定依据。
2. 每条验收标准的结论（通过 / 不通过 / 证据位置）记入 progress.md 验证记录表，作为三维判定 Correctness 的依据。
3. 发现功能错误 → 视同验证失败，触发 DP；规范类问题记录后呈报用户。
4. 项目无测试框架且验收标准无法核对 → 如实记录“深度验证降级”及原因，不得伪造结论；生成测试报告，记录模式、范围、真实命令和输出、未覆盖项及结论。快速工作流路径无 tasks.md 时以用户指定目标和变更意图为依据。

快速工作流路径（tweak/hotfix）仍执行所选模式的验证和测试报告；不强制完整三维判定。

## 三维判定

| 维度 | 判什么 | 怎么判 |
|------|--------|--------|
| Completeness 完整性 | 需求无遗漏 | specs 每条 Requirement 都能对应到已完成的任务与验证义务 |
| Correctness 正确性 | 行为符合契约 | 契约"关键场景/验收检查"逐条比对实现行为 |
| Coherence 一致性 | 改动无越界 | 以 `baseline.review_base` 为基线执行 `git diff --name-only <review_base>..HEAD -- . ':(exclude)<changes_dir>/<change-name>'`（`changes_dir` 读自 workflow.config.md，默认 `openspec/changes/`；含工作区未提交改动时去掉 `..HEAD`），**必须排除变更工件目录本身**（工件、progress.md、state.yaml 是流程产物，不是业务改动）；把输出与契约"任务批次"的文件清单逐项比对。**不得**用 progress.md 里 AI 自己写的"改动文件清单"当证据——那是被审查对象的自述，不是独立证据 |

任何一维不通过：在 progress.md 记录结论与差异说明，触发 DP 交用户决定（回 `/sflow-apply` 修复或放弃变更）。**不得**带着不通过判定进入归档。

## 快速路径收口

hotfix/tweak 不走完整三维判定，但仍须真实执行所选验证链并生成测试报告；所选检查及测试完成后才将模式、范围、报告和结果登记到 `quick-<name>/progress.md`，并在 `quick-<name>/state.yaml` 追加 `verify.passed` 回执后标记收口。

## 阶段报告（强制收尾）

输出末尾必须附共享约定 core.md（sflow-start 母本）第 8 节的四行报告。全部通过时"下一步"为 `/sflow-review`（审查是归档的前置门禁，**不得跳过审查直接归档**）。

## 反模式

- 不得用"应该没问题""类型看着是对的"代替真实执行输出。
- 不得只跑验证链的一部分就宣布通过。
- 不得在验证失败时静默降级结论（如把失败描述成"部分通过"）。
